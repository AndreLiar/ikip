# 0017. SQLAlchemy (ORM/Core) + Alembic (migrations) for the data layer

- **Status:** Accepted
- **Date:** 2026-11-07
- **Deciders:** Architect, PM
- **Related:** FR9–FR14, FR19–FR21 · NFR10, NFR13, NFR15 · Epic 1 (Story 1.5), Epics 2–4 · builds on [ADR 0001](./0001-vector-store-pgvector.md), [ADR 0015](./0015-neon-serverless-postgres.md); supports [ADR 0003](./0003-local-first-ports-and-adapters.md)

## Context
IKIP needs (a) a way to define and query the relational data model (tenant, user, document, version, section, chunk, embedding, …) in Python, and (b) a tool to evolve the schema safely and reversibly across environments (NFR13). The data store is PostgreSQL + pgvector on Neon ([ADR 0001](./0001-vector-store-pgvector.md), [ADR 0015](./0015-neon-serverless-postgres.md)); access is driven by psycopg (v3). The retrieval design is hybrid-and-relational with strict tenant scoping ([ADR 0003](./0003-local-first-ports-and-adapters.md), NFR10), so we want models + a repository layer, not just raw SQL strings.

## Decision
Use **SQLAlchemy 2.0** (ORM + Core) as the data-mapping layer and **Alembic** as the migration tool.

- **SQLAlchemy 2.0** typed models (`Mapped` / `mapped_column`), a declarative `Base`, and a `TenantScoped` mixin; the tenant-scoped repository (`TenantScopedRepository`) is built on SQLAlchemy `select()` so every query is filtered by `tenant_id`.
- **Alembic** for migrations: URL injected from `Settings` (`.env`) so migrations target whichever **Neon branch** is active (dev / ephemeral test / prod); `--autogenerate` from the ORM metadata; migrations reviewed and made **reversible** (e.g., downgrade drops enum TYPEs, not just tables).

## Consequences
**Positive**
- **De-facto standard, mature** Python ORM — huge ecosystem, docs, longevity; 2.0 typing integrates with our type-checked codebase.
- Works natively with **psycopg v3** and Postgres features we need (JSONB, enums, FKs, indexes; pgvector via `pgvector.sqlalchemy` later).
- **Core escape hatch:** when the ORM is the wrong tool (hybrid retrieval, vector ops, window functions), SQLAlchemy Core / raw SQL is available in the same session — no second library.
- **Alembic** gives versioned, reversible, autogenerated migrations that follow the Neon-branch URL — fits per-environment/ephemeral-branch testing (Story 1.5).
- Supports the repository + tenant-scoping pattern cleanly (NFR10).

**Negative / risks**
- SQLAlchemy has a **learning curve** (sessions, identity map, lazy loading); misuse causes N+1 queries or detached-instance bugs.
- **Autogenerate is not magic** — it must be reviewed (it missed dropping enum types here; it doesn't see data migrations or some constraint changes).
- ORM abstraction can **leak**; for vector/hybrid retrieval we will drop to Core/SQL deliberately (expected, not a surprise).

**Neutral**
- Async: we start sync (simpler); SQLAlchemy supports async (`asyncio` + psycopg) if request-path DB latency later warrants it.

## Alternatives Considered
- **Raw SQL + hand-written migrations (e.g., yoyo/dbmate/sqitch):** maximal control, no ORM overhead, but we'd hand-build model mapping, the repository/tenant-scoping, and lose autogenerate — more boilerplate and error-prone for a 13-table model. Rejected.
- **SQLModel (SQLAlchemy + Pydantic, by FastAPI's author):** attractive (unifies API + DB models), but it's a thinner, less-mature layer over SQLAlchemy 2.0, and coupling DB tables to API schemas is often undesirable (we want separate boundaries). We already use Pydantic for API/config and SQLAlchemy for persistence — a clean split. Rejected for the data layer; can still use Pydantic for DTOs.
- **Django ORM:** excellent ORM + migrations, but pulls in the Django framework we don't use (we're FastAPI). Rejected.
- **Tortoise / Peewee / other ORMs:** smaller ecosystems, weaker Postgres/async/typing stories than SQLAlchemy 2.0. Rejected.
- **Alembic alternatives (yoyo, dbmate, sqitch):** fine tools, but Alembic is SQLAlchemy-native (shares metadata, autogenerate) — no reason to split. Rejected.

## Revisit When
- Request-path DB latency needs **async** → adopt SQLAlchemy async engine/session (same library).
- A specific workload is better served by raw SQL end-to-end for a module → use Core/SQL there (already allowed).
- Migration needs outgrow Alembic (unlikely) → reassess.
